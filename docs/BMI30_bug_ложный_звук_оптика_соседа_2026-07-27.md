# BMI30 — ложное звуковое оповещение при молчащей оптике соседа

- Дата расследования: 2026-07-27
- Устройство наблюдения: 7AA5CED27 (node 3, роль slave), IP 192.168.0.163
- Исследованная версия (НЕ для правки): websplit-бандл `2026-07-23-1841`

  - engine: `host/bmi30_active_runtime/project/host/BMI30.200.py.2026-07-23-1841`
  - usb-транспорт: `host/bmi30_active_runtime/project/host/usb_vendor/usb_stream.py`

## 1. Симптом

Оптический датчик физически находится на другом устройстве и во время теста НЕ трогается (молчит).
На данном устройстве звук должен появляться ТОЛЬКО при срабатывании оптики соседа. Однако
**изредка и коротко** звук всё же проскакивает, хотя оптика соседа не срабатывала.

## 2. Конфигурация гейта на устройстве наблюдения

- `optic_reaction_enabled = False` — реакция на СВОЮ оптику выключена.
- `optic_neighbor_reaction_enabled = True` — реакция на оптику СОСЕДА включена.

Следствие: ворота `_optic_detection_gate_allowed()` открываются тогда и только тогда, когда
`_current_neighbor_optic_active()` вернёт `True`, то есть когда ЛЮБОЙ сосед из списка `remote`
отдаёт `optic_active=True`.

## 3. Как звук физически возникает после открытия гейта

В `BMI30.200.py` функция `_fire_beep()` при значении по умолчанию
`BMI30_BEEP_REPEAT_WHILE_HOLD=1` запускает `self._beeper.play_repeating_sequences(...)` —
сигнал **зацикливается в фоновом потоке** бипера. Даже если гейт открылся всего на один цикл
опроса (~0.2 с), успевает проиграться хотя бы один полный короткий сигнал, прежде чем
следующий цикл закроет гейт и вызовет `_stop_sound_now()`. Отсюда «редко и коротко».

Гейт проверяется корректно в точках старта звука (`_fire_beep`, `_beep_hold_start`) и в
обслуживающем цикле `_tick`. То есть проблема НЕ в отсутствии проверки гейта, а в том, что
`_current_neighbor_optic_active()` **изредка ложно возвращает True**.

## 4. Доказательства (живая телеметрия)

Источник данных гейта — фоновый опрос `poll_rs485_sensors()` (EP0 `0x43` GET_RS485_SENSOR,
пакет `SNS1`, 16 байт, **без CRC**), результат складывается в
`/tmp/bmi30_device_state.json` → `sensors.remote[*].optic_active`. Реальная группа: узлы
**0, 1, 2, 3** (3 — локальный). Ниже — лог монитора фронтов `optic 0→1` за один прогон:

```
=== gate watch start 10:39:03 ===
10:39:03 n0  optic ?->0 det1=0 det2=0 lastchg=290457 sb=0x0000 master=1
10:39:03 n1  optic ?->0 det1=0 det2=0 lastchg=0      sb=0x0000 master=0
10:39:03 n2  optic ?->0 det1=0 det2=0 lastchg=123363 sb=0x0000 master=0
10:41:13 n6  optic ?->0 det1=0 det2=0 lastchg=0      sb=0x0000 master=1
10:41:13 n27 optic ?->1 det1=1 det2=0 lastchg=947240 sb=0x0003 master=0   <-- ЛОЖНОЕ optic=1
10:46:32 n12 optic ?->0 det1=1 det2=1 lastchg=1266869 sb=0x0006 master=0
=== gate watch end 10:49:03 ===
```

Ключевые факты из лога и снимков кэша:

1. **Фантомные узлы.** В списке `remote` появляются узлы **n6, n12, n27**, которых в реальной
   группе НЕТ (реальные — 0/1/2/3). Реестр версий ранее уже фиксировал ложные RS485 ID
   (S04/S08/S11/S15) из «несовместимого хвоста STAT v5».
2. **Фантом отдаёт optic=1.** Узел **n27** вернул `optic_active=1` (`sb=0x0003`) — этого
   достаточно, чтобы `_current_neighbor_optic_active()` вернул True и открыл гейт.
3. **Связка indication на мастере.** Ранее наблюдался момент, когда мастер (n0, `master=True`)
   отдавал `optic_active=1` ОДНОВРЕМЕННО с `detadc1=1` и `detadc2=1` (`sb=0xA4BF`, младшие 3 бита
   = `111`), затем всё вместе гасло (`sb=0xA4B8` = `000`). У n1/n2 бит optic всегда 0, а биты
   detadc меняются независимо. Вывод: **на мастере бит `optic` двигается вместе с детекцией —
   это indication/aggregate, а не физический оптический датчик.**
4. **Нестабильность STM32.** Журнал `bmi30-core.service` показывает многократные
   `[HW-RESET] release lines pins=[3,17]`; `last_change_ms` мастера падал с 73053298 до 290457
   (сброс uptime). После сброса `sensor_bits=0x0000`. Фантомные узлы и ложные optic возникают
   в окне нестабильности/после сброса.
5. **STAT версии 5, `sync_layout_valid=False`** на этом устройстве. Прямая RS485-таблица
   надёжна только после перехода STM32 на согласованный STAT v6.

## 5. Разбор корневой причины (по коду)

### 5.1. Фантомные узлы из невалидированного `seen_mask`
`usb_stream.py`, `poll_rs485_sensors()`:

```python
seen_mask = int(sync.get("sync_seen_mask", 0) or 0) & 0xFFFFFFFF
...
node_ids = [
    node_id for node_id in range(32)
    if bool(seen_mask & (1 << node_id)) and node_id != local_node_id
]
...
for node_id in node_ids:
    item = self.get_rs485_sensor(node_id)      # EP0 0x43 по фантомному ID
    if isinstance(item, dict):
        remote.append(item)                     # фантом попадает в remote
```

`seen_mask` берётся из `sync_state` БЕЗ проверки `sync_layout_valid`. При нестабильном STM32
(STAT v5, невалидная раскладка, окно после HW-RESET) `seen_mask` содержит мусорные биты →
host опрашивает несуществующие RS485 ID (6/12/27) → они попадают в `remote`.

### 5.2. Отсутствие CRC и однобитовое решение в SNS1
`usb_stream.py`, `_parse_rs485_sensor_packet()`:

```python
if len(bs) < RS485_SENSOR_V1_LEN or bs[:4] != b"SNS1":
    return None
...
"optic_active":            bool(sensor_bits & 0x0001),
"optic_indication_allow":  bool(sensor_bits & 0x0001),   # ТОТ ЖЕ бит!
```

- У пакета `SNS1` нет CRC — единичный шумовой/переходный ответ, начинающийся с `SNS1` и с
  установленным битом валидности, принимается как достоверный.
- `optic_active` и `optic_indication_allow` — это **один и тот же бит** `sensor_bits & 0x0001`.
  Для мастера этот бит фактически отражает indication/aggregate (см. факт 3), а не физическую
  оптику. Поэтому индикация/детекция мастера читается соседом как «сработала оптика».

### 5.3. Гейт доверяет ЛЮБОму элементу `remote`
`BMI30.200.py`, `_current_neighbor_optic_active()` возвращает True, если хотя бы один элемент
`sensors.remote` имеет `optic_active=True`. Фантомный узел или indication-бит мастера
достаточно, чтобы открыть гейт.

### 5.4. Итоговая причинно-следственная цепочка
```
STM32 нестабилен / STAT v5 / HW-RESET
   → sync_seen_mask мусорный (не проверяется sync_layout_valid)
      → poll_rs485_sensors опрашивает фантомные RS485 ID
         → фантом (или indication-бит мастера) отдаёт optic_active=1  [нет CRC, 1 бит]
            → _current_neighbor_optic_active() = True
               → гейт открывается
                  → _fire_beep()/play_repeating_sequences() → короткий звук
   (следующий цикл закрывает гейт → звук глохнет → «редко и коротко»)
```

## 6. Рекомендованный фикс (для ПОСЛЕДНЕЙ актуальной версии)

Многоуровневая защита (fail-closed), в порядке приоритета:

1. **Отбраковка фантомных узлов (главное).** В `poll_rs485_sensors()` формировать `node_ids`
   только когда раскладка sync валидна (`sync_layout_valid=True`) и только по реально
   присутствующим RS485 ID (`seen`/`recent`/`online`/`local`). При невалидной раскладке —
   не опрашивать по «сырому» `seen_mask` и не публиковать такие узлы в `remote`.

2. **Разделить `optic_active` и `optic_indication_allow`.** Для мастера бит `sensor_bits & 0x01`
   отражает indication, а не физическую оптику. Для гейта соседа использовать ТОЛЬКО признак
   физической оптики; узлы с признаком indication/aggregate (особенно `master=True`, а также
   случаи, когда `optic` встаёт синхронно с `detadc1/detadc2`) не должны трактоваться как
   срабатывание оптики.

3. **Дебаунс/подтверждение соседней оптики.** Открывать гейт по соседу только если
   `optic_active=True` держится непрерывно ≥ окна подтверждения (например 0.30 с — больше
   интервала опроса ~0.2 с; параметр `BMI30_OPTIC_NEIGHBOR_CONFIRM_S`). Любое `False`/`unknown`
   мгновенно сбрасывает таймер (fail-closed). Реальное срабатывание длится секунды и легко
   проходит подтверждение; одиночные фантомные/шумовые сэмплы отсекаются.

4. **Целостность SNS1.** Желательно добавить проверку целостности пакета `SNS1` (CRC или
   строгая валидация полей: `node_id` присутствует в валидном `seen_mask`,
   `node_id_matches_status=True`), чтобы не принимать ответы по фантомным ID.

5. **Прошивка STM32 → STAT v6.** Перевести устройства на согласованный STAT v6 и устранить
   причину HW-RESET (pins 3/17). Это убирает первопричину мусорного `seen_mask`.

> Примечание: пункт 3 (дебаунс) на исследуемой версии был временно опробован и **откачен** по
> требованию — правки на версии `2026-07-23-1841` НЕ вносить. Данный документ предназначен для
> реализации на последней актуальной версии.

## 7. Как воспроизвести/проверить

1. На slave-устройстве: `optic_reaction_enabled=False`, `optic_neighbor_reaction_enabled=True`.
2. Оптику соседа НЕ трогать (должна молчать).
3. Мониторить `/tmp/bmi30_device_state.json` → `sensors.remote[*]`:
   - фиксировать появление узлов вне реальной группы (например 6/12/27);
   - фиксировать `optic_active=1`, совпадающий с фантомом или с `detadc`/`master`.
4. Наблюдать корреляцию таких событий с короткими звуковыми всплесками и с записями
   `[HW-RESET]` в журнале `bmi30-core.service`.
