# Фиксация потери управления устройством после USB-восстановления

## Проблема

После зависания USB и восстановления связи (watchdog stage 2-3) устройство теряет управление:
- Режимы не переключаются (профиль 3 должен показывать 600 семплов, показывает 200)
- Команды отправляются, но не выполняются на устройстве
- Хост-код считает команды успешно выполненными, хотя они не прошли

**Корневая причина**: Хост отправляет команды управления (profile, mode, windows) без проверки подтверждения (ACK) от устройства. После восстановления связи эти команды могут не выполниться на устройстве, но хост-код продолжает работать как будто всё прошло успешно, попадая в несогласованное состояние.

**Ключевое наблюдение**: Перезагрузка хост-кода (БЕЗ перезагрузки STM32) полностью исправляет проблему, подтверждая что ошибка в host-коде, а не в firmware.

## Решение

### 1. Добавлена функция `send_cmd_and_wait_ack()` в USBStream

**Файл**: `host/usb_vendor/usb_stream.py`

Новый метод отправляет команду и **синхронно ждёт ACK (0x80)** перед возвратом:

```python
def send_cmd_and_wait_ack(self, cmd, payload: bytes, ack_timeout_ms=500):
    """
    Отправить команду и ждать ACK (0x80) от устройства перед возвратом.
    
    Returns:
        True если получен ACK (0x80), False если таймаут или ошибка отправки
    """
```

**Логика**:
- Отправляет пакет команды на EP_OUT
- Пытается прочитать ответ (0x80 = RSP_ACK) с EP_IN с таймаутом 100-1000ms
- Возвращает True/False в зависимости от получения ACK

### 2. Обновлены критические команды в BMI30.200.py

Все команды управления режимами теперь используют `send_cmd_and_wait_ack()` и проверяют успешность перед обновлением локального состояния:

#### Обновленные места:

**A. Watchdog-восстановление при повторном подключении** (строка ~1795)
- SET_PROFILE → требует ACK перед продолжением
- SET_FRAME_SAMPLES → проверка
- Частота (0x11) → проверка

**B. Переключение в режим LATEST** (~4055-4120)
- SET_WINDOWS(0,0,0,0) → требует ACK
- SET_STREAM_MODE=0 → требует ACK  
- SET_ASYNC_MODE=1 → требует ACK

**C. Переключение в режим LOSSLESS_ROI** (~4200-4270)
- SET_WINDOWS(280,200,0,0) → требует ACK
- SET_STREAM_MODE=1 → требует ACK
- SET_ASYNC_MODE=0 → требует ACK

**D. Переключение в режим AVG_ROI** (~4370-4450)
- SET_WINDOWS(280,200,280,200) → требует ACK
- SET_STREAM_MODE=2 + avg_n → требует ACK
- SET_ASYNC_MODE=0 → требует ACK

**E. Обновление avg_n во время работы** (~4375)
- SET_STREAM_MODE=2 с новым avg_n → требует ACK

**F. Инициализация потока (initseq)** (~6505-6545)
- SET_WINDOWS(0,0,0,0) → требует ACK
- SET_STREAM_MODE=0 → требует ACK
- SET_PROFILE → требует ACK

### 3. Логика обработки ошибок

При каждой критической команде:
```python
if hasattr(self.stream, 'send_cmd_and_wait_ack'):
    cmd_ok = self.stream.send_cmd_and_wait_ack(CMD_..., payload, ack_timeout_ms=500)
else:
    self.stream.send_cmd(CMD_...)  # Fallback для старых версий
    cmd_ok = True

if not cmd_ok:
    print("[CONTEXT] CMD ACK not received - device may not have accepted change")
    return  # Abort if critical command failed
```

**Стратегия**:
- Если команда не прошла - НЕ обновляется локальное состояние
- Функция возвращает управление, позволяя watchdog или пользователю повторить попытку
- При успешном ACK - логируется "confirmed" для отладки

## Тестирование

После обновления:
1. **Нормальное переключение режимов** → должны работать как раньше (команды выполняются нормально)
2. **После USB-зависания** → watchdog отправляет SET_PROFILE с ACK-проверкой
3. **Если ACK не получен** → логируется ошибка и не обновляется состояние
4. **Режимы 0-2** → теперь требуют подтверждения перед активацией

## Обратная совместимость

Если `send_cmd_and_wait_ack()` не доступен (старая версия USBStream), код использует fallback:
- Вызывает обычный `send_cmd()` и считает операцию успешной
- Сохраняет полную обратную совместимость
