# BMI30 Tag Detection: предложение алгоритма

Документ описывает рабочую модель детекции метки в websplit-системе. Цель -
вернуть физический смысл порога: коэффициент срабатывания должен означать,
насколько сигнал ответа метки превышает текущий уровень шума.

## Главный принцип

Детектор не должен сравнивать одиночный максимальный пик с одиночным
максимальным пиком шума. Это слишком чувствительно к резким выбросам и легко
ломает смысл порога.

Базовая величина должна быть:

```text
S = устойчивая энергия/средний уровень ответа метки в окне сигнала
N = устойчивый средний уровень шума в опорных окнах, где ответа метки быть не должно
trigger = S > K * N
```

Где `K` - пользовательский порог в портале.

## Почему текущий подход опасен

Если брать `S` как максимум 64-битного product, а `N` как максимум только одного
дальнего квартала, детектор может:

- занижать шум, если выбранный квартал оказался тихим;
- принимать одиночный узкий spike за метку;
- почти постоянно срабатывать при выключенных shape-фильтрах;
- терять смысл порога, потому что `K` начинает управлять не отношением
  сигнал/шум, а случайным выбором участка шума.

## Данные для расчета

Работать нужно в реальном 64-битном домене, а не по мониторной картинке:

```text
cur[i]  = current_adc[i] - dc_current
prev[i] = previous_adc_shifted[i] - dc_previous
P[i]    = abs(int64(cur[i]) * int64(prev[i]))
```

Мониторный масштаб может использоваться только для отображения.

## Предобработка

1. Центрировать ADC по устойчивой DC-оценке.
2. Подбирать phase shift до расчета итогового окна сигнала.
3. Не усреднять уже взятые максимумы или `abs(product)` как основной сигнал.
4. Если используется усреднение буферов, усреднять сырые центрированные данные
   или устойчивые признаки, а не одиночные пики.

Важно: увеличение количества буферов усреднения может визуально увеличить
мелкие резкие скачки, если усредняется нелинейная величина (`abs`, max,
product) или если в данных есть когерентная помеха. Случайный шум уменьшается,
а повторяющаяся структура остается и становится заметнее. Поэтому нужно хранить
и показывать не только среднее, но и дисперсию/разброс.

## Поиск кандидата

Для каждого канала:

1. Построить `P[i]`.
2. Найти несколько кандидатов peak position, но не принимать решение по одному
   peak.
3. Для каждого кандидата построить окно ответа метки:

```text
signal_window = [peak - pre, peak + post]
guard_window  = signal_window + запас по обе стороны
```

4. Посчитать сигнал как устойчивую величину по окну:

```text
S_peak = max(P in signal_window)
S_avg  = trimmed_mean(P in signal_window)
S_eng  = sum(P in signal_window) / window_len
S      = комбинация S_avg/S_eng с ограничением по S_peak
```

Рекомендуемый стартовый вариант:

```text
S = percentile(P[signal_window], 80)
```

или

```text
S = mean(top 20% values in signal_window)
```

Так одиночный тонкий spike не станет полноценным сигналом метки.

## Оценка шума

Шум надо измерять рядом по времени, но вне зоны, куда мог попасть ответ метки.

Для кандидата `peak`:

1. Исключить `guard_window`.
2. Взять несколько reference windows слева и справа.
3. Разбить reference windows на короткие блоки.
4. Для каждого блока посчитать устойчивый уровень, например RMS или percentile.
5. Итоговый шум:

```text
N = median(block_levels)
```

или

```text
N = trimmed_mean(block_levels)
```

Если рядом с кандидатом есть явная помеха, блоки с экстремально высоким уровнем
можно исключать только специальным interference-фильтром. Базовый шум не должен
выбираться как самый тихий участок.

Рекомендуемый старт:

```text
block_level = percentile(P[block], 70)
N_frame     = median(block_level)
N_smooth    = EMA(N_frame), если нет принятого trigger
```

## Адаптация шума во времени

Шум меняется постоянно, но сигнал метки не должен попадать в обновление шума.

Правило:

- если кадр не кандидат: быстро обновлять `N_smooth`;
- если есть кандидат, но нет принятого trigger: обновлять медленно;
- если trigger принят: заморозить обновление шума на короткое время;
- release делать по отдельному нижнему порогу, а не тем же `K`.

Пример:

```text
N_smooth = (1 - alpha) * N_smooth + alpha * N_frame
alpha_idle = 0.10
alpha_candidate = 0.02
alpha_trigger = 0.00
```

## Условие срабатывания

Базовое решение без дополнительных фильтров:

```text
R = S / max(N_smooth, N_min)
candidate = R >= K
```

Для устойчивости:

```text
trigger_on  = R >= K
trigger_off = R < max(1.0, K * 0.75)
confirm     = trigger_on держится N последовательных кадров
```

Порог `K=1.0` должен давать много ложных срабатываний. `K=2.0` должен быть
заметно строже. `K=4.0` должен закрывать почти все обычные шумовые события.

## Локализация шума

Локализация нужна не как фильтр, а как защита измерения шума от ответа метки.

Для каждого кандидата:

- если peak в первой половине кадра, нельзя автоматически брать только дальний
  правый квартал;
- если peak в последней части кадра, нельзя автоматически брать только левый
  квартал;
- надо брать несколько окон вне guard zone и усреднять их устойчиво;
- если кандидат сдвигается, reference windows должны сдвигаться вместе с ним.

## Базовая защита от spikes

Даже при выключенных named filters нужна минимальная физическая проверка, что
сигнал похож на ответ метки, а не на один sample spike.

Это не должен быть "фильтр типа метки". Это часть определения `S`.

Минимальные проверки:

- ширина области выше `0.5 * S_peak` не меньше заданного минимума;
- `S_eng / S_peak` не слишком мал;
- соседние samples в signal window дают вклад в `S`.

Если пользователь выключил все фильтры, эти проверки можно сделать мягкими, но
не надо возвращаться к решению по одному максимуму.

## Дополнительные фильтры

Named filters должны работать поверх базового S/N:

- `casino`: ожидаемая форма/двойной отклик/расстояние между компонентами;
- `barkhausen`: широкий ответ, ограничение по общей заполненности кадра;
- `microwire`: узкий короткий ответ;
- `paper`: отдельная форма/длительность.

Отдельные interference-фильтры:

- высокочастотные spikes: много узких выбросов, высокая производная, малая
  интегральная энергия;
- низкочастотная помеха: широкий дрейф, много энергии вне signal window;
- broad burst: высокий уровень во многих reference windows одновременно;
- насыщение/клиппинг ADC.

## Что показывать в портале

Для отладки надо видеть не только итоговый уровень:

- `S` - уровень сигнала;
- `N` - уровень шума;
- `R = S/N`;
- выбранный `K`;
- peak index;
- signal window;
- guard window;
- reference windows;
- причина отказа: `below_ratio`, `too_narrow`, `interference`, `confirm_wait`.

На осциллограмме полезно рисовать:

- окно сигнала;
- окна шума;
- текущий `R`;
- заморожен ли noise update.

## Что нужно для реализации

1. Набор записей player:
   - чистый шум без метки;
   - слабая метка на уровне шума;
   - сильная метка;
   - ложные срабатывания;
   - разные типы помех;
   - разные значения усреднения буферов.

2. Разметка:
   - `Tag U?/Tag L?` для кадров, где метка есть;
   - точный диапазон ответа, если он виден;
   - `Noise`, `Interf`, `False` для отрицательных примеров.

3. Offline analyzer:
   - прогоняет записи;
   - считает `S`, `N`, `R`;
   - строит таблицу false/true при разных `K`;
   - показывает окна на записи.

4. Единая функция detector core:

```text
detect_frame(current, previous, channel, settings) -> DetectionResult
```

Эта функция должна использоваться и player-анализом, и live realtime.

5. После offline-проверки перенести параметры в портал.

## План внедрения

### Этап 1. Документ и offline prototype

Сделать чистую функцию расчета:

```text
P, peak, signal_window, noise_windows, S, N, R, reason
```

Прогнать по существующим `player_recordings`.

### Этап 2. Визуальная проверка

Добавить в player overlay:

- signal window;
- noise windows;
- `S/N`;
- reason.

### Этап 3. Live detector

Заменить текущую смесь peak/noise/shape guards на единый core.

### Этап 4. Фильтры

Добавлять named filters только после того, как базовый S/N работает устойчиво.
